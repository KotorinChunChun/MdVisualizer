# 品質運用

対象範囲の変更、検証結果、未確認事項を同じ版へ記録し、[検証手順](/docs/developer/testing/01-test-strategy.md)に従って確認する。

テスト動画・生ログ・台帳・生成結果は版別logsへ置きGit対象外とする。秘密値は結果やコミットへ記載しない。実行条件は[AGENTS.md](../../../AGENTS.md)、公開の手順は[RELEASE_RULE](../../../dev/RELEASE_RULE.md)、保留中の対象は[保留案](../../../dev/PLAN_IDEAS.md)を参照する。

未導入のCI・coverage等の計画を現行の品質ゲートとして扱わない。

## 検証結果と公開可否の判断

結果には対象範囲、実行コマンド、入力、成否、環境制約、未確認事項を残す。コマンド起動失敗と製品不具合を区別し、実施していない受入を合格にしない。

公開時はproduction build/test、パッケージ生成、版・署名・ハッシュ検証、ステージ、アップロード、公開後の取得確認を順に行う。製品・共有core・Tauri・SPFxの版は各形式の表記規則を含めて照合する。作成しただけでは公開完了としない。

| 失敗 | 次の判断 |
|---|---|
| build/test失敗 | 原因を解消して対象検証を通すまで後続の公開へ進まない |
| 署名・ハッシュ不一致 | ステージせず、対象物と生成元を確認する |
| App Catalog失敗 | SPFxを完了とせず、Web配布の状態は別に記録する |
| FTP一部失敗 | 不足ファイルを特定し、同じ検証済み成果物から再送する |
| 公開物の破損 | 公開停止または直前正常成果物への復旧を判断し、勝手に別版を生成しない |
| 設定移行失敗 | 文書本体を保護し、退避・復旧経路を確認する |

公開後はHTTP成功だけでなくMIME、長さ、取得物のハッシュ、配布記事とリンクの版を照合する。インストール・起動確認は別の結果として記録する。

## 秘密情報と診断

認証情報をコマンド引数、標準出力、コミット、公開artifactへ含めない。診断を共有するときは本文、完全パス、トークン、APIキーなどの混入を確認し、必要な範囲だけを提供する。実行ID、エラー分類、時刻などで追跡できるようにする。

製品の会話・通信記録は一般診断と用途が異なる。本文を含む保持範囲、削除、設定は[AI利用仕様](/docs/user/ui/codex.md)を正本とし、過去の保持件数案を運用へ持ち込まない。

## CI拡張を検討する場合

frontend、Rust、SPFx、ブラウザー操作、秘密・依存・ライセンス点検、配布Plan/WhatIfを責務別のjobに分ける。lockfileと既存のローカルコマンドを使い、CI専用の別手順を増やさない。共用node_modulesで依存導入と別ビルドを競合させない。

CIの導入有無と必須jobは実際の設定から確認する。coverage閾値、通知期限、公開停止の自動化は合意・設定・検証が揃ってから適用する。将来の目標を既存の品質ゲートとして扱わない。
