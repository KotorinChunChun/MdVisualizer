# コードビュー選択時のプレビュー同期負荷に関する検討案

## 背景

コードビューで行を選択すると、その行に対応するビジュアル表示側を表示するため、コードビューとプレビューのスクロール位置を同期する。現在は、行選択時の同期が非常に低速になり、100枚程度の画像や図を含む文書では待ち時間が目立つ。

本資料は、実装を開始する前の原因整理と対策候補を記録する検討案である。既存のスクロール位置保存、折りたたみ解除、検索ジャンプ、ビジュアル表示の仕様を壊さないことを前提とする。

## 現状から推測される負荷箇所

### 1. 行選択から対象要素を探す処理

コード側の行選択を受けると、プレビュー側で`data-source-line`や折りたたみ要素を検索し、対象行を特定する。文書全体を`querySelectorAll`で走査する処理が同期的に実行される場合、画像・Mermaid・表が多い文書ほど探索時間が増える。

### 2. 折りたたみ解除とレイアウト再計算

対象行が折りたたみ内にある場合、親の折りたたみを順に展開してから対象へ移動する。この過程でDOMの高さが変化し、展開後に再度位置を計算する必要がある。画像のロードやMermaidの描画が同時に進んでいると、対象位置が何度も変わる可能性がある。

### 3. `scrollIntoView`による即時スクロール

対象要素へ`scrollIntoView`を実行した直後に、表示位置の補正や選択行のハイライトを行うと、レイアウト確定前のスクロールと補正が連続する。複数回の`requestAnimationFrame`や位置計算が重なると、利用者には同期が遅く見える。

### 4. コード側とプレビュー側の双方向同期

コードスクロール、プレビュースクロール、行選択によるジャンプが互いにイベントを発生させると、同じ移動を再処理する可能性がある。同期中であることを示すフラグや目標値の判定が不十分だと、スクロールイベントの往復が発生する。

### 5. プレビュー全体の再レンダー

行選択に伴う状態更新が`MarkdownPreview`全体の再レンダーを引き起こすと、画像・Mermaid・編集用コンポーネントも再評価される。表示位置の計算だけが目的であれば、選択行の表示状態とプレビュー本文の再生成を分離する必要がある。

## 対策候補

### 案A：行番号から対象要素へのインデックスを事前作成する

プレビュー描画後に、`data-source-line`を持つ要素を1回だけ走査して、行番号から要素への`Map<number, HTMLElement>`を作る。行選択時は全DOM検索を行わず、Mapから対象を取得する。

折りたたみ親についても、対象要素から親の折りたたみIDをたどれるため、行選択のたびに全セクションを走査しない構成にできる。

副作用が比較的小さく、最初に試す候補とする。

### 案B：同期処理を1回の`requestAnimationFrame`へ集約する

行選択イベントが短時間に連続しても、最後の行だけを対象にする。処理を次の1回へ集約する。

1. 最新の対象行をrefへ保存
2. 既に予約済みなら追加処理をしない
3. 次の`requestAnimationFrame`で折りたたみ解除と位置計算を実行
4. レイアウト確定後に1回だけスクロール

古い選択行へのスクロールを途中で実行しないことが重要である。

### 案C：折りたたみ解除とスクロールを2段階に分離する

折りたたみ解除によって高さが変わる場合は、同じフレーム内でスクロール位置を確定させない。

- 第1フレーム：必要な親だけ展開
- 第2フレーム：対象要素の位置を再取得
- 第2フレーム内で1回だけ`scrollIntoView({ behavior: "auto" })`

アニメーションスクロールは同期処理では使わず、処理完了後の利用者操作に限定する。

### 案D：スクロール先の直接設定を優先する

対象位置が取得できる場合は、`scrollIntoView`を何度も呼ばず、プレビューコンテナに対する目標`scrollTop`を計算して1回だけ設定する。上下の余白やヘッダー分を含めた目標値を共通関数で計算する。

ただし、CSS zoom、表示倍率、折りたたみ解除直後のレイアウト、プレゼンテーション表示では計算誤差が出るため、案B・案Cと組み合わせて検証する。

### 案E：スクロール中の状態保存を遅延させる

コードビューとプレビューのスクロールイベントごとにReact stateを更新せず、操作中はrefだけを更新する。スクロール停止後、または一定間隔後に最後の位置だけをstateへ保存する。

これは行選択ジャンプそのものだけでなく、ジャンプ中に発生するスクロールイベントの再レンダー抑制にも有効である。

### 案F：行ハイライトをDOM更新だけで切り替える

選択行のハイライト表示のためにMarkdown全体を再レンダーせず、前回のハイライト要素からクラスを外し、今回の要素へクラスを付け替える。React stateが必要な場合も、本文の再解析・再描画と分離する。

## 推奨する実施順

1. 行選択同期の計測ログを追加する
2. 行番号インデックスを作成する
3. 同期処理を`requestAnimationFrame`で集約する
4. 折りたたみ解除とスクロールを2段階化する
5. スクロール中のstate更新を遅延する
6. それでも遅い場合に画像・Mermaidの画面外描画抑制と組み合わせる

最初から仮想スクロールへ移行する案は採用しない。行ジャンプ、折りたたみ、検索、右クリックによるブロック操作、印刷と同時に検証する必要があり、影響範囲が大きいためである。

## 計測項目

100枚の500×500埋め込み画像サンプルを基準に、次を比較する。

- 行選択イベントから対象要素取得までの時間
- 折りたたみ解除に要した時間
- 対象要素取得からスクロール完了までの時間
- 行選択から画面移動完了までの合計時間
- 同期中に発生したレイアウト計算回数
- 同期中の`scroll`イベント回数
- 同期中の長時間タスクとフレーム落ち
- 選択行とプレビュー側ハイライト行の一致

### 受入条件案

- 通常文書と100枚画像文書のどちらでも、同一行の選択から表示完了までの待ち時間が大きく悪化しない
- 連続して別の行を選択した場合、最後に選択した行へ直接移動する
- 折りたたみ内の行でも、必要な親だけが展開される
- コード側とプレビュー側のスクロールが無限に往復しない
- スクロール位置保存、検索ジャンプ、印刷、行ハイライトが既存どおり動作する
- 画像・Mermaid・表の表示内容が再同期によって壊れない

## 保留事項

- DOMインデックスをどのタイミングで再構築するか
- Markdown再描画後のインデックス無効化条件
- 折りたたみ解除中に画像サイズが変化した場合の再計算回数
- コードビュー選択と通常スクロールの同期方向をどこまで共通化するか
- 実測なしに仮想スクロールを導入しないこと
